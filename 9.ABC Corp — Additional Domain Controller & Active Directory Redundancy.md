
हमारे ABC Corp Windows Server 2025 lab में अब तक हम `ABC-DC01` को अपने मुख्य Domain Controller के रूप में इस्तेमाल कर रहे हैं। इसी server पर हमारा Active Directory domain `abc.lab` स्थापित है, जिसके माध्यम से हम domain users, computers, authentication और दूसरी Active Directory-related services को manage करते हैं। अभी तक हमारा lab एक ही Domain Controller पर आधारित था, इसलिए हमने Active Directory की initial configuration और domain environment को समझने के लिए एक server से शुरुआत की थी। लेकिन जैसे-जैसे हम एक वास्तविक corporate network की तरह अपने lab को विकसित कर रहे हैं, हमें यह भी समझना होगा कि अगर हमारा मौजूदा Domain Controller किसी कारण से काम करना बंद कर दे, तो उस स्थिति में हमारी व्यवस्था कैसे काम करेगी।

इसी समस्या को समझने और उसका practical solution implement करने के लिए हमने अपने Linux Mint host पर KVM/QEMU virtualization के अंदर एक नई Windows Server 2025 virtual machine install की है। इस नए server का नाम `ABC-DC02` रखा गया है, जबकि हमारा पहला Domain Controller `ABC-DC01` ही रहेगा। अब हमारा उद्देश्य इस नए server को उसी existing `abc.lab` domain में एक Additional Domain Controller के रूप में configure करना है। इस configuration के माध्यम से हम अपने lab में यह सीखेंगे कि एक domain में multiple Domain Controllers कैसे काम करते हैं, उनके बीच Active Directory directory data किस प्रकार replicate होता है, DNS services की availability कैसे बढ़ाई जा सकती है और एक Domain Controller unavailable होने पर दूसरा Domain Controller किन परिस्थितियों में services उपलब्ध कराने में मदद कर सकता है।

इस practical implementation के पीछे का मुख्य उद्देश्य केवल दूसरा Windows Server install करना नहीं है। हमें यह समझना है कि किसी कंपनी को Additional Domain Controller की आवश्यकता क्यों होती है और उससे कौन-सी समस्या हल होती है। मान लो कि ABC Corp में employees अपने computers पर domain accounts से sign in करते हैं। उनके computers को domain controllers की आवश्यकता users को authenticate करने, Active Directory information प्राप्त करने और domain-related services locate करने के लिए पड़ सकती है। अगर हमारे पास केवल `ABC-DC01` है और वह server किसी hardware failure, operating system problem, network issue या service failure के कारण unavailable हो जाता है, तो कुछ domain-dependent operations प्रभावित हो सकती हैं। पहले से sign-in किए हुए कुछ users cached credentials के कारण अपने computers में logon कर सकते हैं और दूसरी स्वतंत्र network services भी चलती रह सकती हैं, लेकिन हम यह मानकर नहीं चल सकते कि सभी domain-related operations पहले की तरह काम करती रहेंगी।

यही वह परिस्थिति है जिसके लिए हम दूसरा Domain Controller तैयार कर रहे हैं। अगर `ABC-DC02` को सही तरीके से promote किया गया है, उसकी Active Directory और DNS services उपलब्ध हैं और clients तक उसकी network connectivity बनी हुई है, तो वह कई आवश्यक operations के लिए दूसरे Domain Controller के रूप में काम कर सकता है। इस प्रकार हम अपनी directory services को एक ही server पर निर्भर रहने से बचाने की दिशा में आगे बढ़ते हैं। Real-world infrastructure में इसी तरह के design को Domain Controller redundancy और availability planning का हिस्सा माना जाता है।

यहाँ हमें एक महत्वपूर्ण अंतर भी समझना है। Additional Domain Controller का मतलब यह नहीं है कि हम पहले server की एक offline backup copy बना रहे हैं। एक सामान्य writable Additional Domain Controller अपनी Active Directory database रखता है और दूसरे Domain Controllers के साथ directory changes replicate करता है। इस कारण वह स्वयं Active Directory services उपलब्ध कराने में सक्षम होता है। दूसरी ओर, backup और recovery का उद्देश्य जरूरत पड़ने पर पहले की सुरक्षित स्थिति से data को restore करना होता है। अगर कोई administrator गलती से user account delete कर देता है या कोई गलत directory change दूसरे DC तक replicate हो जाता है, तो replication अपने आप उस गलती से सुरक्षा नहीं देती। इसलिए वास्तविक कंपनी में redundancy और backup दोनों की अपनी अलग भूमिका होती है।

हमारे वर्तमान lab में दोनों Domain Controllers एक ही physical computer पर KVM/QEMU की मदद से चलेंगे। इसका अर्थ है कि हम एक virtual machine को बंद करके या उसके operating system को unavailable करके दूसरे Domain Controller के व्यवहार का परीक्षण कर सकते हैं। लेकिन यदि हमारा पूरा physical host बंद हो जाए, तो दोनों virtual machines भी unavailable हो सकती हैं। इसलिए इस lab से हम logical redundancy और replication को practically समझ पाएँगे, लेकिन इससे यह साबित नहीं होगा कि हमने independent hardware failure से सुरक्षा भी हासिल कर ली है। वास्तविक corporate deployment में इस आवश्यकता के अनुसार अलग physical servers या अलग virtualization hosts पर Domain Controllers रखे जा सकते हैं।

हमारे lab की network configuration पहले से निर्धारित है। ABC Corp का internal lab network `ABC-LAB` है, जिसका subnet `192.168.50.0/24` और gateway `192.168.50.1` है। हमारे existing Domain Controller `ABC-DC01` का IPv4 address `192.168.50.10` है। अब `ABC-DC02` को भी इसी lab network में configure करना है, लेकिन उसका IP address अलग और उपलब्ध होना चाहिए। इसलिए हम उसकी network configuration को देखकर ही नया static address निर्धारित करेंगे; बिना जाँच किए कोई IP address assign नहीं करेंगे। इसी तरह DNS settings भी हमारे existing Active Directory environment के अनुरूप configure की जाएँगी।

अब हम actual configuration की शुरुआत करते हैं। चूँकि `ABC-DC02` पर Windows Server 2025 install हो चुका है, इसलिए हमारा पहला काम यह जाँचना है कि नया server वर्तमान में किस स्थिति में है। Windows Server की initial installation के बाद केवल hostname दिखाई देना पर्याप्त नहीं होता। हमें यह भी देखना है कि server का hostname सही है या नहीं, उसका network adapter किस virtual network से जुड़ा है, IPv4 configuration क्या है और DNS client किस server को इस्तेमाल कर रहा है। अगर इन prerequisites को सही किए बिना हम सीधे Domain Controller promotion शुरू कर दें, तो domain discovery, DNS resolution या promotion prerequisite checks में समस्याएँ आ सकती हैं।

इसलिए हम `ABC-DC02` को boot करेंगे और Windows Server के desktop पर पहुँचने के बाद Server Manager तथा network adapter की settings देखेंगे। सबसे पहले hostname verify करेंगे। हमारा intended hostname `ABC-DC02` है। यदि installation के समय यह नाम पहले से निर्धारित किया जा चुका है, तो हमें इसे दोबारा बदलने की आवश्यकता नहीं होगी; केवल actual hostname verify करना पर्याप्त होगा। यदि नाम अलग है, तो उसे सही करके restart पूरा करेंगे और फिर आगे बढ़ेंगे। इसके बाद हम network adapter की IPv4 properties खोलकर current IP address, subnet mask, default gateway और DNS server entries की जाँच करेंगे।

Network configuration में हमारा उद्देश्य नए server को `ABC-LAB` network के साथ align करना है। चूँकि हमारा subnet `192.168.50.0/24` है, इसलिए server का IPv4 address इसी subnet के भीतर होना चाहिए और किसी दूसरे device के address से conflict नहीं करना चाहिए। Subnet mask इस network के अनुरूप होना चाहिए। Default gateway हमारे established lab configuration के अनुसार `192.168.50.1` है, बशर्ते इस virtual network में वही gateway वास्तव में configured और reachable हो। DNS के लिए हमें यह सुनिश्चित करना है कि नया server हमारे existing Active Directory domain को resolve कर सके। Domain Controller promotion से पहले नए server को ऐसे DNS server का उपयोग करना चाहिए जो `abc.lab` की आवश्यक Active Directory DNS information resolve कर सके। हमारे environment में इसके लिए existing `ABC-DC01` का DNS महत्वपूर्ण होगा।

Network configuration पूरी होने के बाद अगला चरण `ABC-DC02` को existing `abc.lab` domain में join करना है। इस कदम का उद्देश्य नए Windows Server को हमारे पहले से स्थापित Active Directory domain का member बनाना है। Domain join और Domain Controller promotion के बीच अंतर समझना आवश्यक है। Domain join होने के बाद server domain membership प्राप्त करता है, लेकिन वह अभी अपने आप Domain Controller नहीं बन जाता। Domain Controller बनने के लिए हमें अलग से AD DS role install करना होगा और promotion wizard पूरा करना होगा।

Domain join करने के लिए हम Windows Server पर System Properties खोलेंगे और computer name तथा domain membership बदलने वाले विकल्प में जाकर domain के रूप में `abc.lab` दर्ज करेंगे। इसके बाद आवश्यक domain credentials देंगे। Creator के वीडियो में उसके अपने domain के credentials इस्तेमाल किए गए हैं; हमारे lab में हम ABC Corp के लिए उपयुक्त authorized domain credentials इस्तेमाल करेंगे। Credentials स्वीकार होने और domain join सफल होने पर Windows Server confirmation देगा। इसके बाद server को restart करना होगा, ताकि domain membership से संबंधित परिवर्तन प्रभावी हो सकें।

Restart के बाद हम फिर से server में sign in करेंगे और यह verify करेंगे कि `ABC-DC02` अब `abc.lab` domain का member है। यदि domain join सफल नहीं होता, तो हम सीधे आगे बढ़ने के बजाय DNS resolution, server connectivity, hostname और credentials की जाँच करेंगे। इसका कारण यह है कि domain join की सफलता इस बात पर निर्भर करती है कि client server existing Domain Controller को locate कर सके और उससे आवश्यक communication कर सके।

अब जब `ABC-DC02` domain member के रूप में तैयार हो चुका है, तो हम इसे Domain Controller बनाने की दिशा में आगे बढ़ सकते हैं। इसके लिए Windows Server में Active Directory Domain Services यानी AD DS role install करना आवश्यक है। AD DS वह server role है जो Windows Server को Active Directory directory services उपलब्ध कराने के लिए आवश्यक components प्रदान करता है। केवल AD DS role install कर देने से server का promotion पूरा नहीं होता; role installation के बाद हमें promotion wizard के माध्यम से उसे existing domain का Additional Domain Controller बनाना होगा।

इस चरण में हम `ABC-DC02` पर Server Manager खोलेंगे और **Manage → Add Roles and Features** चुनेंगे। Wizard में **Role-based or feature-based installation** का विकल्प चुनकर server pool में `ABC-DC02` select करेंगे। इसके बाद Server Roles में **Active Directory Domain Services** को select करेंगे। Windows आवश्यक supporting features जोड़ने का विकल्प दिखाएगा, जिसे स्वीकार करने के बाद हम wizard के अगले चरण पूरे करेंगे और installation शुरू करेंगे। Installation पूरी होने के बाद Server Manager में promotion के लिए notification दिखाई देगी।

AD DS role install होने के बाद अब वास्तविक Domain Controller promotion शुरू होगा। Server Manager की notification से **Promote this server to a domain controller** विकल्प खोलेंगे। क्योंकि हमारा `abc.lab` domain पहले से मौजूद है और हम नया domain या forest नहीं बनाना चाहते, इसलिए deployment configuration में **Add a domain controller to an existing domain** का विकल्प चुनेंगे। यह चुनाव हमारे objective के अनुरूप है: `ABC-DC02` को उसी existing domain का दूसरा Domain Controller बनाना है, न कि अलग domain बनाना या नया forest स्थापित करना।

Wizard में domain के रूप में `abc.lab` verify करेंगे और आवश्यक credentials की पुष्टि करेंगे। इसके बाद Domain Controller Options में DNS Server तथा Global Catalog के विकल्प दिखाई देंगे। हमारे intended lab design में हम नए Domain Controller पर DNS Server और Global Catalog दोनों को enabled रखने का उद्देश्य रखते हैं। DNS Server से domain की DNS availability बढ़ाने में सहायता मिल सकती है, जबकि Global Catalog forest-wide directory searches और कुछ logon-related operations में उपयोगी होता है। फिर भी, इन विकल्पों को चुनने के बाद उनकी actual availability और configuration को promotion पूरा होने पर verify करना आवश्यक होगा।

उसी wizard में Active Directory site का चयन भी करना होगा। हमारे established lab में site का नाम `ABC-HO` है, इसलिए हम इसी site को चुनेंगे, बशर्ते वह wizard में उपलब्ध हो। Active Directory Sites and Services में site और subnet mapping का उद्देश्य servers और clients की network topology को सही ढंग से represent करना है। Site selection को केवल display name की तरह नहीं देखना चाहिए; बाद में हमें यह भी verify करना होगा कि हमारा lab subnet सही site से mapped है और Domain Controller उसी topology के अनुरूप काम कर रहा है।

इसके बाद wizard Directory Services Restore Mode यानी DSRM password माँगेगा। DSRM एक विशेष recovery mode है, जिसका उपयोग Domain Controller की directory services से संबंधित maintenance और recovery operations में किया जाता है। इसका password सामान्य domain administrator password से अलग माना जाना चाहिए और इसे सुरक्षित रूप से manage करना आवश्यक है। हम यहाँ एक मजबूत password निर्धारित करेंगे, लेकिन वास्तविक password को screenshots, GitHub documentation या किसी सार्वजनिक project file में दर्ज नहीं करेंगे।

Promotion wizard में prerequisite checks चलाए जाएँगे। इन checks का उद्देश्य यह verify करना है कि server promotion के लिए आवश्यक conditions पूरी करता है या नहीं। यदि wizard सफल prerequisite-check result दिखाता है, तो हम उसे ध्यान से पढ़ेंगे और फिर installation शुरू करेंगे। यदि कोई warning या error आता है, तो उसे बिना समझे ignore नहीं करेंगे। विशेष रूप से DNS configuration, domain connectivity, credentials, replication source और आवश्यक permissions से संबंधित messages को समझना जरूरी है।

Restart के बाद हम sign in करके Server Manager की स्थिति देखेंगे और पुष्टि करेंगे कि `ABC-DC02` सही तरीके से start हुआ है। फिर Active Directory Users and Computers खोलकर domain की directory structure inspect करेंगे। Domain join के समय computer account सामान्यतः Computers container में दिखाई दे सकता है, लेकिन Domain Controller promotion पूरा होने पर संबंधित computer account Domain Controllers OU में दिखाई देना चाहिए। इस जाँच से हमें यह पुष्टि करने में मदद मिलेगी कि server को वास्तव में Domain Controller के रूप में promote किया गया है।

## अब verify करते हैं कि ABC Corp की Domain Controller redundancy सही काम कर रही है

`ABC-DC02` को existing `abc.lab` domain में promote करने के बाद हमें यह सुनिश्चित करना है कि दोनों Domain Controllers एक-दूसरे के साथ communicate कर पा रहे हैं और directory information replicate हो रही है। इसके लिए हर DNS record या GUI property का screenshot लेने की जरूरत नहीं है। हम कुछ ऐसी जाँच करेंगे जिनके परिणाम से network connectivity, domain discovery और Active Directory replication की वास्तविक स्थिति समझ में आएगी।

सबसे पहले `ABC-DC02` पर PowerShell खोलकर `ipconfig /all` चलाएँगे। इससे हमें पता चलेगा कि नए server पर कौन-सा IPv4 address, subnet mask, gateway और DNS server configured है। इसके बाद `ping 192.168.50.10` से existing `ABC-DC01` की IP connectivity जाँचेंगे। Ping सफल होना network reachability का उपयोगी संकेत है, लेकिन यह अकेले Active Directory services के स्वस्थ होने का प्रमाण नहीं है। इसी तरह ping fail होने पर भी बिना अतिरिक्त जाँच के यह निष्कर्ष नहीं निकालेंगे कि Domain Controller पूरी तरह unavailable है।

अब हम DNS के माध्यम से domain को locate करने की जाँच करेंगे। `ABC-DC02` पर यह command चलाएँगे:

`nslookup -type=SRV _ldap._tcp.dc._msdcs.abc.lab`

इसका उद्देश्य यह देखना है कि DNS हमें `abc.lab` domain के लिए LDAP service उपलब्ध कराने वाले Domain Controllers की जानकारी दे रहा है या नहीं। Output में दोनों servers की जानकारी दिखाई दे सकती है, यदि उनके records सही तरीके से registered हैं और DNS query सही server से की जा रही है। यह जाँच हमें DNS-based DC discovery के बारे में जानकारी देती है, लेकिन directory replication की सफलता अपने आप साबित नहीं करती।


इसके बाद हम Active Directory replication की स्थिति जाँचेंगे। `ABC-DC02` पर elevated PowerShell या Command Prompt खोलकर `repadmin /replsummary` चलाएँगे। यह command replication partners के बीच हुई replication activity और failures की summary देती है। हम विशेष रूप से देखेंगे कि कोई replication failure report हो रहा है या नहीं। यदि failures दिखाई देते हैं, तो उन्हें केवल इस आधार पर ignore नहीं करेंगे कि ADUC में दोनों Domain Controllers और domain objects दिखाई दे रहे हैं। जरूरत पड़ने पर `repadmin /showrepl` से संबंधित replication partners और naming contexts की अधिक विस्तृत स्थिति जाँचेंगे।

यदि DNS या replication से संबंधित कोई समस्या सामने आती है, तो अगली जाँच के रूप में `dcdiag /test:dns` इस्तेमाल कर सकते हैं। यह Domain Controller की DNS-related functionality, service availability और आवश्यक DNS records की जाँच में मदद करता है। इसे हर बार बिना कारण चलाने के बजाय तब इस्तेमाल करेंगे जब हमें DNS configuration की विस्तृत verification या troubleshooting करनी हो।

इन जाँचों के बाद हम परिणाम दर्ज करेंगे: क्या `ABC-DC02` सही network पर है, क्या DNS domain services को locate कर पा रहा है और क्या Active Directory replication में कोई failure दिखाई दे रहा है। इन परिणामों के आधार पर हम तय करेंगे कि हमारा initial redundancy setup सही स्थिति में है या आगे troubleshooting की जरूरत है।
