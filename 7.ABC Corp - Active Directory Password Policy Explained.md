
ABC Corp में हमने Windows Server 2025 पर Active Directory Domain Services (AD DS) configure किए हैं। अब हमारा अगला कदम केवल users और computers को domain से जोड़ना नहीं है, बल्कि यह समझना भी है कि domain में users की security centrally कैसे manage की जाती है।

किसी organization में अनेक users अपने computers पर काम करते हैं। यदि हर user अपने हिसाब से password चुनता रहे और password security के लिए कोई consistent rule न हो, तो organization के लिए account security को manage करना कठिन हो सकता है। इसी आवश्यकता को पूरा करने के लिए Active Directory में Password Policy और Account Lockout Policy जैसी settings का उपयोग किया जाता है।

इस practical में हम इन policies को केवल configure करने के बजाय उनका पूरा workflow समझेंगे। पहले देखेंगे कि Client PC पर वर्तमान में कौन-सी policy प्रभावी है। फिर Domain Controller पर जाएँगे और समझेंगे कि domain-level policy कहाँ manage होती है। इसके बाद Client पर लौटकर देखेंगे कि Group Policy refresh और verification किस तरह काम करते हैं।

इससे हमें यह भी समझ आएगा कि **policy configure करने की जगह और उसके प्रभाव को verify करने की जगह अलग क्यों हो सकती है।**

## 1. Client पर मौजूदा Password Policy देखन

हम शुरुआत `ABC-CLIENT01` से करेंगे। यह हमारे domain environment का Client PC है, जहाँ हम Windows की मौजूदा policy स्थिति देख सकते हैं।

किसी security setting को बदलने से पहले उसकी वर्तमान स्थिति जानना उपयोगी होता है। इससे हमें पता चलता है कि पहले से कौन-सी settings मौजूद हैं और बाद में किसी बदलाव का प्रभाव किस तरह पहचाना जा सकता है।

इसके लिए Windows में `rsop.msc` उपलब्ध है। इसका पूरा नाम _Resultant Set of Policy_ है। यह computer पर लागू Group Policy settings का resultant view दिखाने में मदद करता है।

Client पर Run खोलकर `rsop.msc` चलाएँ। इसके बाद निम्न path पर जाएँ:

![](z_attached%20image/Pasted%20image%2020261013221320.png)

`Computer Configuration → Windows Settings → Security Settings → Account Policies`

![](../Attachments/Pasted%20image%2020261013183342.png)

यहाँ **Password Policy** और **Account Lockout Policy** दिखाई दे सकती हैं। Password Policy में password history, maximum password age, minimum password length और complexity जैसी settings देखी जा सकती हैं। Account Lockout Policy में असफल logon attempts के बाद account lock होने से संबंधित settings मिलती हैं।

शुरुआत में हमने `ITADMIN` domain account से login करके यह जाँच की, लेकिन उस session में हमें अपेक्षित Password Policy settings दिखाई नहीं दीं। 

![](z_attached%20image/Pasted%20image%2020261013221326.png)

इसके बाद हमने logout करके Windows installation के समय बनाए गए local account `labadmin` से login किया और `rsop.msc` दोबारा चलाया। इस बार **Computer Configuration** के अंतर्गत Password Policy और उसकी settings दिखाई दीं।

इससे हमारी lab में यह महत्वपूर्ण observation सामने आया कि अलग-अलग login sessions में RSoP का दिखाई देने वाला परिणाम अलग था। हालाँकि, केवल इस अनुभव से यह निष्कर्ष नहीं निकाला जा सकता कि सभी domain users के पास कम privileges होने के कारण Windows उनसे Password Policy छिपाता है। वास्तविक अंतर account permissions या RSoP के परिणामों के संदर्भ में हो सकता है।

इस चरण में हम केवल मौजूदा configuration को समझ रहे हैं। अभी कोई setting नहीं बदलेंगे।

## 2. Domain Controller पर Central Policy Configuration समझना

Client पर मौजूदा policy देखने के बाद अब हम `ABC-DC01` पर जाएँगे। यहाँ हमारा उद्देश्य यह समझना है कि Active Directory domain के लिए security policy कहाँ manage की जाती है।

Windows Server में Group Policy Management के माध्यम से Group Policy Objects (GPOs) को manage किया जाता है। हमारे domain `abc.lab` में `Default Domain Policy` एक महत्वपूर्ण GPO है, जिसमें domain-level account policies की configuration देखी जा सकती है।

Server पर **Server Manager → Tools → Group Policy Management** खोलें। फिर इस hierarchy को expand करें:

==🟡`Domains → abc.lab → Group Policy Objects`==

यहाँ ==🟠`Default Domain Policy`== पर right-click करके **Edit** चुनें। Group Policy Management Editor में इस path पर जाएँ:

==🟡`Computer Configuration → Policies → Windows Settings → Security Settings → Account Policies`==

अब हम उसी Password Policy और Account Lockout Policy की settings को central configuration के संदर्भ में देख रहे हैं, जिन्हें पहले Client पर inspect किया था।

यहाँ एक महत्वपूर्ण अंतर समझना है: Client पर resultant policy देखना और Server पर GPO की configuration देखना एक ही काम नहीं है। Server पर हम policy की configuration देखते हैं, जबकि Client पर हम यह समझते हैं कि उस computer पर कौन-सी policy settings प्रभावी हैं।

इस चरण में भी settings को बदलने की आवश्यकता नहीं है। पहले मौजूदा configuration को समझेंगे।

## 3. Client पर Policy Refresh और Verification

Server पर policy configure या modify किए जाने के बाद Client को updated Group Policy प्राप्त करके process करनी होती है। Windows नियमित background refresh करता है, लेकिन आवश्यकता पड़ने पर policy refresh को manually request भी किया जा सकता है।

इसके लिए Client पर Command Prompt या PowerShell में यह command इस्तेमाल की जा सकती है:

==🟢`gpupdate /force`==

यह command Group Policy को refresh और process करने का अनुरोध करती है। इसका उद्देश्य नई policy बनाना नहीं, बल्कि configured policies को Client पर update करना है।

Refresh के बाद हम फिर `rsop.msc` खोलकर `Account Policies` तक जाएँगे और उपलब्ध settings देखेंगे। यदि कोई policy बदली गई थी, तो अब हम Client पर दिखाई देने वाले परिणाम की तुलना Server पर देखी गई configuration से कर सकते हैं।

इस तरह workflow पूरा होता है: पहले Client पर मौजूदा स्थिति देखना, फिर Server पर central configuration समझना और अंत में Client पर policy के प्रभाव को verify करना।

## 4. Summery of the topic 

इस practical में हमने सीखा कि ABC Corp के domain `abc.lab` में **Password Policy** को centrally Domain Controller (`ABC-DC01`) पर `Group Policy Management → Domains → abc.lab → Default Domain Policy → Computer Configuration → Policies → Windows Settings → Security Settings → Account Policies → Password Policy` में configure किया जाता है। यहाँ password history, maximum और minimum password age, minimum password length, password complexity तथा reversible encryption जैसी settings manage की जाती हैं। Server पर ==🟩 `gpupdate /force`== चलाने से Server की Group Policy refresh होती है, लेकिन Client पर policy changes refresh करने के लिए यही command `ABC-CLIENT01` पर भी चलानी होती है। इसके बाद Client पर ==🟩 `rsop.msc`== खोलकर resultant policy verify की जाती है। इस workflow से हमने समझा कि **policy configure करना, Group Policy refresh करना और Client पर उसके प्रभाव को verify करना अलग-अलग steps हैं।**
