
## 1. FSMO Role actual में क्या है?

जब हम Windows Server में Active Directory Domain Services (AD DS) चलाते हैं, तो एक ही Domain Controller पर निर्भर रहने के बजाय हम कई Domain Controllers (DCs) रख सकते हैं। ये DCs directory information को replicate करते हैं और सामान्य operations को संभालते हैं।

लेकिन Active Directory के कुछ खास operations ऐसे हैं जिनके लिए एक निश्चित DC को designated responsibility देना जरूरी है। इसी व्यवस्था को **FSMO (Flexible Single Master Operations)** कहा जाता है।

FSMO कोई अलग software, अलग application या ऐसी independent Windows service नहीं है जिसे administrator manually start करके चलाए। यह Active Directory में कुछ विशेष operations के लिए **role ownership और जिम्मेदारी तय करने का mechanism** है। इन roles के अनुसार AD DS संबंधित operations को process करता है।

इसे ABC Corp की management structure से समझ सकते हैं। कंपनी में HR, Sales और Accounts के काम अलग-अलग जिम्मेदारियों के अंतर्गत होते हैं। सभी employees सामान्य काम कर सकते हैं, लेकिन कुछ खास फैसलों के लिए एक designated authority तय होती है। इसी तरह Active Directory में भी सभी operations को एक DC पर नहीं रखा जाता, लेकिन कुछ विशेष operations के लिए FSMO role-holder तय होता है।

यह analogy समझने के लिए है; FSMO roles सामान्य administrative permissions या delegation का विकल्प नहीं हैं।

Active Directory में कुल पाँच FSMO roles होते हैं:

- **Schema Master**
    
- **Domain Naming Master**
    
- **RID Master**
    
- **PDC Emulator**
    
- **Infrastructure Master**
    

इनमें से दो forest-wide roles हैं और तीन domain-wide roles हैं। इसका अर्थ है कि ये पाँच roles पाँच अलग-अलग servers पर रखना अनिवार्य नहीं है। एक DC कई roles रख सकता है। एक single-domain forest में पाँच FSMO roles होते हैं; हर अतिरिक्त domain के साथ तीन domain-wide roles और जुड़ते हैं।

## 2. Forest-wide और Domain-wide roles में अंतर

|Scope|Roles|इसका मतलब|
|---|---|---|
|Forest-wide|Schema Master, Domain Naming Master|पूरे forest के लिए प्रत्येक role का एक designated owner|
|Domain-wide|RID Master, PDC Emulator, Infrastructure Master|प्रत्येक domain के लिए इन तीनों roles का एक designated owner|

**Forest-wide** का अर्थ है कि जिम्मेदारी पूरे Active Directory forest से संबंधित है। **Domain-wide** का अर्थ है कि जिम्मेदारी किसी विशेष domain के भीतर लागू होती है।

इसलिए अगर `ABC.lab` forest में केवल एक domain है, तो उसमें पाँचों roles होंगे। यदि उसी forest में `Mumbai.ABC.lab` नाम का child domain जोड़ा जाता है, तो forest-wide roles वही रहेंगे, लेकिन नए domain के अपने RID Master, PDC Emulator और Infrastructure Master होंगे।

## 3. ABC Corp की business story — FSMO Roles कहाँ काम आते हैं?

मान लो ABC Corp अभी Ahmedabad में काम कर रही है। कंपनी में लगभग 80 employees हैं और उसका Active Directory domain `ABC.lab` है। Users, computers, groups और permissions इसी directory के माध्यम से manage किए जाते हैं।

अब management Mumbai में नया operations centre खोलने और कर्मचारियों की संख्या 300 तक बढ़ाने का फैसला करती है। IT team को नए computers और user accounts बनाने के साथ-साथ application requirements, domain structure, password security और cross-domain access की भी planning करनी है।

इसी business expansion के दौरान FSMO roles की अलग-अलग जिम्मेदारियाँ relevant होती हैं।

### 3.1 नई application को directory में बदलाव चाहिए — Schema Master

ABC Corp अपने internal email और calendar environment के लिए Microsoft Exchange Server Subscription Edition deploy करने पर विचार करती है। Infrastructure team पहले product की supported configuration और deployment prerequisites verify करती है। यदि deployment के लिए Active Directory schema extension जरूरी है, तो team approved change window में schema preparation की योजना बनाती है।

Schema Active Directory का blueprint है। यह निर्धारित करता है कि directory में किस प्रकार के objects और attributes मौजूद हो सकते हैं। Schema modification के लिए forest में एक designated authority होती है—Schema Master।

Application setup या उसका preparation process schema extension शुरू करता है; Schema Master स्वयं software install नहीं करता और न ही सभी prerequisites check करता है। उसका महत्व schema modification की designated authority होने में है।

**Business connection:** जब application की जरूरत Active Directory के blueprint में बदलाव की मांग करती है, तब Schema Master relevant होता है।

### 3.2 Mumbai के लिए नया domain बनाना — Domain Naming Master

Management चाहती है कि Mumbai की IT administration को Ahmedabad से अलग domain में manage किया जाए, जबकि दोनों offices उसी Active Directory forest का हिस्सा रहें। Architecture team नया child domain `Mumbai.ABC.lab` बनाने का निर्णय लेती है।

यह केवल दूसरा Domain Controller जोड़ना नहीं है। यह forest में एक नया domain जोड़ने का operation है। Domain Naming Master forest में domains और trees जोड़ने या हटाने से जुड़े operations का designated owner होता है।

Authorized administrator उपयुक्त tools और credentials के साथ domain-creation process शुरू कर सकता है। उसे अनिवार्य रूप से उसी DC पर login करने की जरूरत नहीं होती जहाँ Domain Naming Master role मौजूद है। Role ownership और administrator permissions अलग चीजें हैं।

यदि Mumbai में केवल दूसरा DC जोड़ा जाए और नया domain न बनाया जाए, तो इस वजह से Domain Naming Master का कोई नया domain-addition operation नहीं आएगा।

**Business connection:** नया office अपने-आप नया domain नहीं बनाता। जब architecture में forest के भीतर नया domain जोड़ने का फैसला होता है, तब Domain Naming Master relevant होता है।

### 3.3 नए employees के accounts बनाना — RID Master

Mumbai office के लिए HR 300 नए employees की list भेजता है। IT team users, computers और security groups बनाने की तैयारी करती है।

हर security principal की Security Identifier (SID) होती है। SID का अंतिम हिस्सा Relative Identifier (RID) होता है। Domain Controllers अपने उपलब्ध RID pools से RIDs इस्तेमाल करके नए security principals बनाते हैं।

जब किसी DC को अतिरिक्त RIDs की जरूरत होती है, तो RID Master उसे RID pool allocate करता है। इसका अर्थ यह नहीं है कि हर user creation के लिए DC को RID Master से अनुमति लेनी पड़ती है। DC अपने उपलब्ध pool से सामान्य account creation करता रहता है।

यदि किसी DC का RID pool खत्म हो जाए और वह नया pool प्राप्त न कर सके, तो नए security principals बनाने का operation fail हो सकता है। पहले से उपलब्ध RIDs होने पर DC उनका उपयोग जारी रख सकता है।

**Business connection:** बढ़ती hiring के दौरान अलग-अलग DCs users बना सकते हैं, जबकि RID allocation की designated authority domain में identifiers की uniqueness बनाए रखने में मदद करती है।

### 3.4 Password changes और domain time — PDC Emulator

Mumbai में काम शुरू होने के बाद Rahul अपना password Ahmedabad के DC पर बदलता है। उसी समय वह Mumbai के किसी application में login करने की कोशिश करता है। यदि Mumbai का DC अभी password change replicate नहीं कर पाया है, तो वह नए password को reject कर सकता है। ऐसी स्थिति में वह PDC Emulator से नवीनतम password-related जानकारी check कर सकता है।

PDC Emulator password-related operations, account-lockout handling और domain time hierarchy में महत्वपूर्ण भूमिका निभाता है। यह हर login request को अपने पास नहीं खींचता और न ही बाकी DCs की जगह लेता है।

इस role का नाम पुराने Windows NT के Primary Domain Controller model से आया है, लेकिन आधुनिक Active Directory में भी इसकी विशेष जिम्मेदारियाँ बनी हुई हैं।

**Business connection:** जब कई DCs वाले domain में password changes, lockouts और time consistency को संभालना हो, तब PDC Emulator relevant होता है।

### 3.5 दूसरे domain के users को access देना — Infrastructure Master

Mumbai की application team चाहती है कि Ahmedabad के कुछ IT employees को Mumbai के applications का access मिले। इसके लिए `Mumbai.ABC.lab` में `Mumbai-App-Access` नाम का security group बनाया जाता है और Ahmedabad domain के Rahul account को उसमें member जोड़ा जाता है।

Rahul का account `ABC.lab` में ही रहता है। उसे Mumbai domain में दूसरा account बनाकर duplicate करने की जरूरत नहीं है।

बाद में HR Rahul का account एक OU से दूसरी OU में move करता है। इससे उसके Distinguished Name (DN) का path बदल सकता है, जबकि उसी user object का SID सामान्यतः वही रहता है। Cross-domain references को maintain करने में Infrastructure Master की भूमिका हो सकती है।

यह role Rahul का account दूसरे domain में copy नहीं करता और न ही उसकी application permissions तय करता है। यह cross-domain object references की maintenance से संबंधित है।

**Business connection:** जब एक domain के objects के references दूसरे domain में इस्तेमाल होते हैं, तब Infrastructure Master relevant हो सकता है। Single-domain forest में इसका काम सामान्यतः कम दिखाई देता है।

## 4. Role transfer इतना आसान है, तो इनकी importance क्या है?

FSMO roles को command या graphical interface से transfer किया जा सकता है। लेकिन इसका मतलब यह नहीं कि roles का कोई वास्तविक महत्व नहीं है या उन्हें मनमाने ढंग से बार-बार बदलना चाहिए।

Role transfer का उद्देश्य designated ownership को बदलना है—उदाहरण के लिए, planned maintenance, role-holder को decommission करना या किसी वास्तविक operational जरूरत के कारण जिम्मेदारी दूसरे DC को देना।

मान लो DC02 पर RID Master role है और DC04 पर users बनाए जा रहे हैं। DC04 अपने उपलब्ध RID pool से accounts बनाता है। उसे हर user creation के लिए DC02 से अनुमति नहीं लेनी पड़ती। जब अतिरिक्त RID pool चाहिए, तब RID allocation mechanism काम करता है।

यदि DC02 की planned maintenance होनी है, तो appropriate planning के बाद RID Master role को दूसरे suitable DC पर transfer किया जा सकता है। इससे DC04 का user-creation काम किसी नए permission workflow पर निर्भर नहीं हो जाता; केवल RID allocation की designated authority बदलती है।

इसी प्रकार, Schema Master को transfer करने से दूसरे DC पर कोई अलग software install नहीं होता। Schema modification की designated authority बदलती है। Domain Naming Master को transfer करने से administrator privileges अपने-आप नहीं बदलते। Administrator को अब भी आवश्यक permissions चाहिए।

इसलिए FSMO roles को पाँच अलग-अलग software packages या सामान्य background services के रूप में नहीं देखना चाहिए। ये Active Directory के भीतर विशेष operations के लिए निर्धारित ownership assignments हैं।

Windows Server पर elevated Command Prompt या PowerShell में यह command चलाएँ:

`netdom query fsmo`

इस command का उपयोग role ownership verify करने के लिए करें; यह अपने-आप कोई role transfer नहीं करती।

| RID Master            | Active Directory Users and Computers → domain पर right-click → Operations Masters → RID            |
| PDC Emulator          | Active Directory Users and Computers → domain पर right-click → Operations Masters → PDC            |
| Infrastructure Master | Active Directory Users and Computers → domain पर right-click → Operations Masters → Infrastructure |

## 6. अंतिम समझ

FSMO roles Active Directory के भीतर कुछ विशेष operations के लिए designated responsibility तय करते हैं। सामान्य directory operations कई DCs पर चलते रहते हैं, जबकि इन चुनिंदा operations के लिए एक निश्चित role-holder होता है।

ABC Corp की कहानी में application की schema requirement, नया domain जोड़ना, नए employees के लिए RID allocation, password-related coordination और cross-domain references—हर परिस्थिति में अलग FSMO role relevant होता है।

**FSMO को समझने का सही तरीका है: पहले business requirement पहचानो, फिर Active Directory में होने वाला operation समझो, और उसके बाद उस operation से संबंधित role को पहचानो।** केवल role transfer command याद कर लेना configuration सीखना है; उस role की आवश्यकता और operational effect समझना वास्तविक learning है.
